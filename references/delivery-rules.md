# User-selected delivery

Ask only for missing information affecting saving: chat-only, local file or connected document. Reuse confirmed destinations and permissions. Do not assume DingTalk, an account or a path.

- Chat-only: return content without automatically creating files or external documents.
- Local: use the chosen directory and format. Markdown is a portable fallback when no rich format is requested. Use available DOCX/PDF tooling and its required verification for those formats. Follow workspace rules and keep task materials outside skill directories.
- Online: use the user's platform, available connector and required workflow. DingTalk, Notion, Google Docs, Microsoft 365 and others are possible destinations, not integrations bundled here. Do not install connectors or switch platforms without authorization.

JD, interview questions and candidate records may have separate destinations. Do not reuse a previous role's documents for a new role unless instructed.

Read targets first. Preserve existing content, structure, styles, attachments and numbering. Default to H1 candidate sections with score in the name; supplements can be H3 within the entry. Match the user's existing format. Append new candidates once and update existing ones when new evidence arrives; preserve sources and explain score changes.

After saving, read back to verify content and destination. Inspect current state before retrying a failed or timed-out write to prevent duplicates; follow connector retry limits. Report partial/failed delivery honestly. If online access is unavailable, finish the content in chat; save a local alternative only if authorized, and never describe it as a successful online update.

Keep private mappings and preferences in permitted task notes or memory, outside the distributable skill. Reconfirm only a materially changed destination or destructive operation whose authority is missing.

## Preserve established record templates

Before adding to an existing interview record, inspect an earlier correctly formatted entry in the platform’s native block structure. Preserve the attachment position relative to sections and copy the interview-summary container type, visual attributes and editable blank paragraphs. A matching text heading is not equivalent to a callout/highlight container; Markdown placeholder syntax is not evidence of native formatting. Do not append resumes at the document end when the established template places them earlier. Preserve entered feedback, schedules, scores and attachment resource identities. Keep private document IDs and candidate information in task notes.

After writing, verify actual attachment order and summary block type/attributes, in addition to text completeness. Report structural verification separately from visual preview; do not claim visual QA without inspecting the rendered result.

## Required DingTalk candidate-entry layout

Unless the user explicitly requests a different layout, apply both rules whenever writing a candidate analysis into a DingTalk interview record:

1. Insert the original resume as a native attachment/preview immediately after the complete candidate screening conclusion section (候选人甄选结论), before recruitment conditions/background (招聘条件与专业背景). If that background section is absent, place the attachment before the next analysis section. Never leave it at the candidate-entry end or document end. Preserve the original attachment resource when moving an existing resume.
2. Place the initial-interview summary between the interview questions and follow-up recommendations. Use a native highlight/callout container with the pin sticker/icon (钉子), containing “初试总结：” and at least one editable blank paragraph. Reuse the existing correct container’s structure and visual attributes. Do not substitute an H2/H3 heading plus an ordinary paragraph, literal Markdown fences, or “待面试填写” placeholder text. Preserve any feedback already entered instead of clearing it.

Read back the native structure and verify attachment order, highlight-container type, pin icon and editable paragraphs before reporting completion. If the platform cannot create the required container, report the formatting limitation; do not silently deliver a plain-text substitute. These layout rules do not authorize writing to DingTalk without the user’s established delivery permission.
